# Running-order vectors

Rounding logs from committee phones, each with the running order a phone holding them must show
(#68). The Dart rule, `runningOrders` in `packages/core/lib/src/roundings.dart`, is held to them by
`packages/core/test/running_order_vectors_test.dart`, and so is burgee once it vendors them.

## Direction: pro-companion is canonical, burgee vendors

**pro-companion is canonical for this set, and burgee vendors it**, as for `fixtures/scoring/` and
`fixtures/chain/` (groom decision G32 on #12; ADR 005 point 4, "Chain and rounding fixtures:
companion → burgee"). A change to a vector is made here first, and burgee's copy follows it. burgee
copies this directory unchanged, `SHA256SUMS` included; the drift check that compares its copy
against this manifest is held story H87.

## Expected orders are worked out by hand

Every expected order was worked out by hand from the rule below, and the steps are kept in the
vector's `working` field. **Expected orders are never generated by the Dart rule**, nor by burgee's
or any other implementation. A vector produced by running the code it is meant to check would pass
that code by construction. When an implementation disagrees with a vector, the vector is worked
again by hand before either side changes.

## The rule

Owner decisions at #68's pickup, 2026-10-27.

1. **The race.** For each fleet, the race is the fleet's latest gun not recalled or undone, when it
   went on the reading phone's local date of `now`. With no such gun it is the fleet's race of the
   day. A rounding stamped with a gun (`payload.race`) is in that gun's race only. One stamped with
   none was tapped on a phone that knew no gun. It is in the race of the day it was tapped on, and,
   once a gun is known, in that gun's race when its `device_ts` is at or after the gun's time.
2. **The boat.** A rounding counts for the latest sail number a `rounding.sail` names for it
   (`corrects_ulid`), else the one it was tapped with. A rounding nobody has named counts for no
   boat, and is counted as `unnamed`. A rounding a `rounding.undo` names counts for nothing.
3. **The order.** A boat with more roundings in the race is ahead: the log has no course, so how
   many marks she has rounded is how far round she is. Boats level on that are in the order they
   rounded their latest mark. A boat's latest rounding is found in two steps: on each phone, the one
   it logged last (highest `seq`); then, of those, the latest by `device_ts`.
4. **The clocks.** Boats level on roundings whose latest roundings are on one phone are in the order
   that phone logged them, by `seq`: that is the order they were tapped, even across a clock set on
   the phone. Across phones (a gate's two mark boats), each rounding is moved to satellite
   time by its phone's latest `clock.offset` before it, by sequence number: `device_ts + offset_ms`.
   Where any of them has no offset with an `offset_ms`, the group is ordered on the phones' own
   clocks instead, each phone's own boats then put back in its `seq` order in the places they hold,
   and `clocks_unmatched` is true. A ULID is minted from its phone's clock, so it is never a stand-in
   for `seq`.
5. **Waiting marks.** A mark some phone is stationed at, with no rounding of the fleet in the race,
   is `waiting`: its roundings have not arrived, so the order shown does not include it. A phone
   whose role picks are in the log keeps its station only under its role pick in force. For a phone
   whose role picks are not (they are logged before it is admitted, so never reach shore), its
   latest station pick not undone stands. Either way the pick counts only when made on the reading
   phone's local date of `now`. Waiting marks are listed in the standard set's order
   (`docs/marks.md`).
6. **The fleets.** One order per fleet the day defines (`fleet.defined`), in the order defined, or
   one for the single fleet (`null`) when it defines none. Roundings that name no fleet on a day
   that defines fleets are an order of their own, last.

## Format

`pro-companion-running-order-vector/1`. Each file holds:

- `now`: when the phone reads the order, in milliseconds since the epoch. Every vector sits between
  12:00 and 12:30 UTC on 2026-10-24, so its events fall on one local date in every time zone, and
  a day-old event on the date before.
- `events`: the log, each event with only the envelope fields the rule reads: `ulid`, `device_id`,
  `seq`, `device_ts`, `kind`, `corrects_ulid` where it has one, and `payload`. Events the rule never
  reads, such as role picks on a phone with no station, are left out.
- `expected`: one entry per fleet, in order: the `fleet` id, the `race` gun's ULID or null, the
  `order` (each boat's `sail`, her `roundings` in the race, and the `mark` of her latest), `unnamed`,
  `waiting` and `clocks_unmatched`.
- `working`: how the expected order was worked out.

## Coverage

| Vector | Criterion | What it holds |
|---|---|---|
| `a-one-mark-race-of-the-day` | 1 | one mark's order; no gun, so the race of the day; yesterday's rounding left out |
| `b-later-mark-is-further` | 2 | boats round the second mark ahead of those that have rounded only the first |
| `c-corrections-and-undo` | 3 | a wrong number corrected, an unidentified boat named, an undone rounding, one never named |
| `d-a-mark-still-waiting` | 4 | a stationed mark with no roundings is waiting; an undone station and an undone role are not |
| `e-fleets-and-race-boundaries` | 1 | two fleets; an earlier race's rounding and one before the gun are left out |
| `f-a-gate-in-satellite-time` | 1 | a gate's two phones put in order through their clock offsets, against their raw clocks |
| `g-a-gate-on-unmatched-clocks` | 1 | one phone with no offset measured: raw clocks, and `clocks_unmatched` |
| `h-a-clock-set-back-on-one-phone` | 1, 4 | one phone's tap order across its clock set back; yesterday's station is not waiting |
